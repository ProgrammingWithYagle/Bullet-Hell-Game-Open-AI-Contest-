# Recovery implementation and verification boundary

Protocol 4. The signed checkpoint, SQL ledger, authenticated HTTP adapter and server lifecycle journal are implemented and tested locally. They are not connected to public gameplay recovery, hosted D1 or global rankings.

Game.authoritativeCheckpoint() retains the current multiplayer roster, builds, supplies, timers, votes, RNG, offered/selected contracts, mutations and bounded purchase-reply history at lobby/intermission boundaries. Restore validates the state, clears transport input and leaves participants disconnected. The complete action library and historical departed roster are separate unfinished work.

src/server/checkpoints.ts signs exact serialized bytes with a server-only HMAC-SHA-256 key of at least 32 bytes. UUIDv4 run ID, owner epoch, sequence and 24-hour expiry are verified. Altered/noncanonical/oversized data and unsafe phases are rejected. Its one-MiB serializer ceiling is independent of the smaller transport bound; a fifty-player serializer round-trip does not prove a fifty-player HTTP recovery path.

src/server/run-store.ts executes conditional ownership/sequence/digest/state changes and event insertion in one SQL batch. A NOT NULL guard aborts a zero-row compare-and-set. It covers identical-payload retries, conflicts, ninety-second leases, epoch increments, stale checkpoints, finalization and a latched Practice downgrade for interrupted combat. Settings and cumulative counters cannot decrease through an accepted boundary. The SQL migrations are in services/run-ledger/migrations/.

src/server/run-auth.ts and run-service.ts implement the private Practice checkpoint transport: POST /v1/runs/register, /v1/runs/event and /v1/runs/lookup. Lookup requires writer authentication and returns private recovery data; it is not the public finalized-result API in LEADERBOARDS.md. Requests are bounded UTF-8 JSON, at most 64 KiB, with unknown fields rejected. Key ID and server ID are checked against deployment configuration. Unix timestamp seconds permit at most 300 seconds of skew; a 128-bit nonce is retained for ten minutes in SQL. HMAC-SHA-256 signs method, exact path, time, nonce and SHA256_HEX(exact body bytes), with a canonical base64url signature verified through Web Crypto. Query strings, tampering, unknown keys/servers and replay fail authentication. Ranked registrations are explicitly rejected until the ranking finalizer exists.

src/server/run-client.ts uses a five-second request timeout, bounded responses and redirect rejection. HTTPS is required except HTTP loopback for local tests. Optional Sites service access is sent only to the exact configured origin. No actual deployment secret is generated or configured by these tests, and none belongs in browser/Electron assets, source, public JSON or URLs.

src/server/run-journal.ts coordinates acknowledged registration/boundaries before combat-start, thirty-second lease renewal, finalization and restart claims. One uncertain transport response gets one retry with the same event ID/payload and a fresh HTTP nonce. Wrong acknowledgements, exhausted retries and expired leases latch the journal unavailable; a later successful call cannot silently promote it again. Finalization here closes recovery and does not submit scores.

src/server/room-journal.ts now connects this journal to GraveRoom through a server-only createGameServer factory. No browser/matchmaking option can configure a writer. The normal executable has no factory configured and continues as Practice with checkpoint status disabled. A configured room freezes its lobby/intermission clock and input/vote/purchase mutations while writing the exact boundary and combat-start. Joins, drops, reconnects and departures wait for that barrier. Lease refresh does not stop active combat; a new intermission waits for an in-flight lease before saving. Terminal victory/defeat closes the journal. Disposal prevents a delayed acknowledgement from starting combat, and does not manufacture a finalize event during shutdown.

Clients receive status only after their ready handshake; the welcome message supplies current status for late arrivals. New AI-authored messages in all fifteen locales describe checkpoint waits and a latched service outage. Practice may continue after an outage, while recoveryAvailable remains explicitly false. Acknowledged means a server checkpoint was written, not that participant restoration is available. Checkpoints are saved on safe phase entry and immediately before deployment; purchases/votes made later in an intermission are not individually durably acknowledged. The next captured boundary preserves them. Command-level durable acknowledgements and participant restoration remain unfinished.

tests/room-journal.test.ts exercises real SQLite with delayed acknowledgements, safe clocks, automatic deployment, nonblocking lease refresh, permanent outage status, finalization and disposal. tests/room-journal-network.test.ts adds two actual local WebSocket clients: a frozen purchase cannot spend coins, an arriving player waits and is included in the next combat checkpoint, and outage status reaches the client while Practice advances. Controlled delays, synthetic victories and local SQL adapters are not hosted-D1 or human/device evidence. Latest complete verification passes 74 tests, strict TypeScript, 15-locale checks and a production build. New status layout has not been rendered-browser reviewed.

tests/run-service.test.ts runs actual local HTTP, exact-byte tampering/format vectors, durable nonce checks, unknown-field/ranked rejection, conflicts, outages and redirect non-forwarding. tests/run-journal.test.ts starts a separate loopback HTTP process against a temporary file-backed SQLite database, stops it, starts a replacement and races two restore claimants. Exactly one owner wins; the saved roster/build/supplies/cards/votes/RNG and duplicate-purchase reply survive. Old-owner writes and finalized restores fail. Interrupted combat requires explicit Recovery Practice. Lease time is advanced by an isolated test-process IPC clock, not by waiting ninety seconds. Synthetic victories and temporary generated test keys are not human gameplay, natural crash timing or deployed-D1 evidence. An initial assertion compared signed versus unsigned representations of the same RNG bits; the corrected check verifies canonical bits and the next RNG output. The failed output is retained under reviews/recovery/.

Cloudflare documents atomic batch rollback in the [D1 Database API](https://developers.cloudflare.com/d1/worker-api/d1-database/). Real SQLite transactions verify these statements locally; they do not establish actual hosted-D1 races.
